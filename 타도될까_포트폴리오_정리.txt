# 프로젝트 정리: 타도될까

## 포트폴리오 요약

### 1. 문제 정의

버스를 이용할 때 사용자가 알고 싶은 것은 단순한 승차 인원이 아니라, **“지금 이 버스를 타도 괜찮은지”**에 대한 즉각적인 판단이다. 하지만 서울시 버스 승·하차 공공데이터는 월별·노선별·정류장별·시간대별 집계값으로 제공되어, 일반 사용자가 원본 데이터만으로 혼잡 여부를 판단하기 어렵다.

이 프로젝트는 공공데이터를 사용자의 탑승 의사결정에 필요한 정보로 변환하여, 버스 노선과 정류장, 시간대를 선택하면 예상 혼잡도와 더 한산한 탑승 시간을 보여주는 것을 목표로 했다.

### 2. 해결 과정

1. 서울 열린데이터광장의 12개월치 버스 승·하차 데이터를 수집했다.
2. 시간대별 값이 여러 컬럼에 퍼져 있는 원본 CSV를 `pandas.melt()`로 세로형 데이터로 변환했다.
3. 월별 총 승차 인원을 해당 월의 일수로 나누어 시간대별 일평균 인원을 계산했다.
4. 승차 인원을 기준으로 `여유·보통·혼잡·매우 혼잡` 네 단계의 혼잡도로 구분했다.
5. RandomForestClassifier 학습 파이프라인을 구성하고, 서비스 운영 단계에서는 요청마다 대용량 데이터나 Python 모델을 실행하지 않도록 조회용 JSON 캐시를 생성했다.
6. React 화면에서 검색 결과를 숫자만 나열하지 않고, 혼잡도·피크 시간·한산한 시간·행동 추천 문구로 시각화했다.

### 3. 기술 구조

- **Frontend — React 18, Vite, styled-components, Recharts**  
  검색 조건을 입력받고 API를 호출한 뒤, 선택 시간의 혼잡도와 24시간 추이, 피크·추천 시간을 보여준다.
- **Backend — Node.js, Express**  
  노선·정류장 옵션, 시간대별 혼잡도, 단건 예측 API를 제공하고, 최초 요청 시 JSON 캐시를 메모리의 Map으로 변환해 조회한다.
- **Data/ML — Python, pandas, scikit-learn**  
  CSV 수집·정제·변환, 혼잡도 라벨 생성, RandomForest 학습, API용 캐시 생성을 하나의 파이프라인으로 구성했다.

`CSV 공공데이터 → Python 전처리/학습 → JSON 캐시 → Express API → React 시각화`

### 4. 핵심 기능

- 기준 월과 버스 노선, 정류장, 탑승 시간 검색
- 선택한 시간대의 예상 승차 인원과 4단계 혼잡도 제공
- 24시간 승차 인원을 막대그래프로 시각화하고, 선택 시간과 피크 시간을 강조
- 피크 시간 TOP 3와 한산한 시간 TOP 3 안내
- “지금 타도 괜찮아요”와 같은 행동 중심의 탑승 추천 제공
- 월별 데이터가 없을 때 전체 노선·정류장 목록을 사용하는 fallback 처리

### 5. 성과

- **12개월치 공공데이터를 서비스화**했다. 약 674개 노선과 약 509,541개의 월·노선·정류장 시리즈를 검색 가능한 구조로 변환했다.
- 원본 CSV의 복잡한 가로형 구조를 분석·API 응답에 적합한 세로형 구조로 표준화했다.
- 대용량 데이터 계산을 사전 캐시 생성 단계로 이동시켜, 실제 API는 메모리 기반 조회로 응답하도록 설계했다.
- 데이터 수집부터 전처리, 모델 학습, API, 프론트엔드 시각화까지 전체 흐름을 하나의 웹 서비스로 구현했다.

> 응답 속도 개선은 구조적으로 확인되지만, 전·후 벤치마크 수치는 아직 측정하지 않았다. 포트폴리오에서는 “응답 속도를 N% 개선했다”고 표현하기보다 “실시간 계산을 메모리 조회로 변경했다”고 설명하는 것이 정확하다.

### 6. 회고

가장 큰 배움은 **모델을 만드는 것과 실제 서비스에서 사용하는 것은 별개의 문제**라는 점이었다. RandomForest 학습 구조를 구성했지만, 현재 서비스의 실제 응답은 사전 생성한 캐시와 고정 임계값 라벨을 사용한다. 이로 인해 서비스 응답은 단순하고 빠르게 유지했지만, 모델의 예측 가치를 실제 사용자 결과로 연결하지 못했다는 한계가 남았다.

또한 원본 데이터가 월별 집계 데이터이기 때문에 실시간 혼잡도, 평일·주말 차이, 공휴일·날씨·행사의 영향을 반영할 수 없었다. 다음 버전에서는 실시간 버스 위치와 요일, 날씨 데이터를 결합하고, 노선 전체에 같은 기준을 적용하는 고정 임계값 대신 노선별 분위수 기준을 사용해 혼잡도의 실질적인 의미를 높이고자 한다.

## 1. 프로젝트 개요

`타도될까`는 서울시 공공데이터인 "버스노선별 정류장별 시간대별 승하차 인원 정보"를 기반으로, 사용자가 버스 노선과 정류장, 기준 월, 시간대를 선택하면 해당 시간대의 예상 혼잡도와 추천 탑승 시간을 보여주는 웹 서비스이다.

핵심 목적은 "지금 이 버스를 타도 괜찮을까?"라는 사용자의 일상적인 판단을 데이터 기반으로 도와주는 것이다.

서비스는 React 기반 프론트엔드, Express 기반 백엔드 API, Python 기반 데이터 전처리/모델 학습 스크립트로 구성되어 있다.

데이터명:

- 기본 월은 `202605`
- 노선 수는 약 674개

## 5. 데이터 전처리

전처리 파일은 `backend/model/preprocess.py`이다.

원본 데이터는 시간대별 승하차 인원이 가로 컬럼으로 들어 있다.

예:

00시승차총승객수, 00시하차총승객수, 1시승차총승객수, ...

이를 pandas의 `melt()`를 사용해 세로 형태로 변환한다.

전처리 후 데이터 구조:

{
  "route": "160",
  "station": "강남역",
  "dayType": "all",
  "hour": 8,
  "passengers": 42.3,
  "alightPassengers": 31.1,
  "crowding": "보통",
  "isWeekend": 0
}

월별 총 승객 수는 해당 월의 일수로 나누어 "일 평균 승객 수"로 변환한다.

혼잡도 라벨 기준:

0 ~ 20명: 여유
21 ~ 50명: 보통
51 ~ 80명: 혼잡
81명 이상: 매우 혼잡

## 6. 모델 학습 구조

학습 파일은 `backend/model/train_model.py`이다.

사용 모델:
- RandomForestClassifier

입력 피처:

route
station
dayType
hour
isWeekend
passengers
alightPassengers

타깃:

crowding

학습 파이프라인:
1. CSV 로드
2. 가로 시간대 컬럼을 세로 형태로 변환
3. 승차 인원 기준 혼잡도 라벨 생성
4. 범주형 변수는 OneHotEncoder 처리
5. 숫자형 변수는 passthrough
6. RandomForestClassifier 학습
7. 모델을 `bus_crowding_model.pkl`로 저장
8. 전처리 데이터를 `processed_bus_data.pkl`로 저장
9. API 응답 최적화를 위한 `bus_api_cache.json` 생성

현재 서비스 API는 요청마다 Python 모델을 실행하지 않고, 미리 생성된 `bus_api_cache.json`을 메모리에 올려 빠르게 응답한다. 즉, ML 학습 구조는 존재하지만 실시간 서비스 응답은 캐시 기반 룩업 + 혼잡도 라벨링 방식이다.

## 8. 주요 API 명세

### 8.1 옵션 조회

GET /api/bus/options

프론트 초기 로딩 시 사용한다.

응답 예시:

{
  "routes": ["0017", "01A", "01B", "040", "0411"],
  "months": [
    {
      "value": "202506",
      "label": "2025년 6월"
    }
  ],
  "defaultMonth": "202605",
  "dayTypes": ["all", "weekday", "weekend"],
  "hours": [0, 1, 2, 3, ..., 23]
}

실제 데이터의 `dayTypes`는 `all`만 존재하지만, API에서는 프론트 호환성을 위해 `weekday`, `weekend`도 fallback으로 포함한다.

### 8.2 노선별 정류장 목록 조회

GET /api/bus/stations?route=160&month=202605

필수 query:
- `route`

선택 query:
- `month`

응답 예시:

{
  "route": "160",
  "month": "202605",
  "stations": ["강남역", "남대문시장", "서울역버스환승센터"]
}

월별 정류장 목록이 있으면 해당 월 기준으로 반환하고, 없으면 전체 노선 정류장 목록을 fallback으로 사용한다.

### 8.3 시간대별 혼잡도 조회

GET /api/bus/hourly?route=160&station=강남역&month=202605&dayType=all

필수 query:
- `route`
- `station`

선택 query:
- `month`
- `dayType`

응답 예시:

[
  {
    "hour": 0,
    "passengers": 12,
    "crowding": "여유"
  },
  {
    "hour": 1,
    "passengers": 5,
    "crowding": "여유"
  },
  {
    "hour": 8,
    "passengers": 63,
    "crowding": "혼잡"
  }
]

프론트의 핵심 화면은 이 API를 사용해 전체 시간대 데이터를 받은 뒤, 선택한 시간의 결과와 피크 시간, 한산한 시간, 차트를 계산한다.

### 8.4 단건 예측 조회

GET /api/bus/predict?route=160&station=강남역&hour=8&month=202605&dayType=all

필수 query:
- `route`
- `station`
- `hour`

선택 query:
- `month`
- `dayType`

응답 예시:

{
  "route": "160",
  "station": "강남역",
  "month": "202605",
  "hour": 8,
  "dayType": "all",
  "predictedCrowding": "혼잡",
  "expectedPassengers": 63,
  "recommendation": "8시는 혼잡도가 높습니다. 가능하면 9시 이후 이용을 추천합니다."
}

## 9. API 캐시 데이터 구조

캐시 파일:

backend/model/bus_api_cache.json

최상위 구조:

{
  "months": [],
  "defaultMonth": "202605",
  "routes": [],
  "routeStations": {},
  "monthRouteStations": {},
  "dayTypes": ["all"],
  "hours": [0, 1, 2, ..., 23],
  "series": {}
}

`series`의 key 형식:

month|||route|||station|||dayType

예:

202506|||N37|||종로2가사거리(00089)|||all

value 형식:

[
  [0, 0, 0, "여유"],
  [1, 0, 0, "여유"],
  [2, 6, 5, "여유"]
]

각 배열 의미:

[hour, passengers, alightPassengers, crowding]

Express 서버는 이 JSON을 최초 요청 시 한 번 읽고, Map으로 변환해 메모리에 캐싱한다.

내부 lookup key:

month|||route|||station|||dayType|||hour

## 10. 프론트엔드 동작 흐름

핵심 화면 파일:

frontend/src/pages/BusCrowdingPage.jsx

동작 순서:
1. 페이지 진입 시 `/api/bus/options` 호출
2. 사용자가 노선을 선택하면 `/api/bus/stations` 호출
3. 사용자가 정류장과 시간대를 선택하고 검색
4. `/api/bus/hourly` 호출
5. 받은 시간대별 데이터를 기반으로 프론트에서 다음 값을 계산
   - 선택 시간의 예상 승객 수
   - 혼잡도
   - 추천 문구
   - 가장 한산한 시간 TOP 3
   - 피크 시간 TOP 3
   - 혼잡도 퍼센트
   - 시간대별 막대그래프 데이터

프론트 API 래퍼:

fetchOptions()
fetchStations(route, month)
fetchHourly(params)

npm run dev

## 13. 포트폴리오에서 강조할 만한 점

1. 공공데이터를 실제 서비스 형태로 가공했다.
2. 월별/노선별/정류장별/시간대별 데이터를 검색 가능한 구조로 변환했다.
3. 원본 CSV의 가로형 시간대 데이터를 분석에 적합한 세로형 데이터로 전처리했다.
4. RandomForest 기반 혼잡도 분류 모델 학습 파이프라인을 구성했다.
5. 대용량 데이터를 매 요청마다 계산하지 않고 JSON 캐시로 변환해 API 응답 속도를 개선했다.
6. React에서 시간대별 혼잡도, 추천 시간, 피크 시간, 한산한 시간 등을 직관적으로 시각화했다.
7. 사용자가 "지금 탈지 말지" 바로 판단할 수 있도록 결과를 숫자보다 행동 추천 중심으로 설계했다.

## 14. 현재 한계와 개선 가능성

현재 데이터는 월별 집계 데이터라 실시간 혼잡도나 요일별 차이를 정확히 반영하지 못한다. `weekday`, `weekend` 옵션은 API 호환성을 위한 fallback이며 실제 데이터는 `all` 기준이다.

개선 방향:
- 실시간 버스 위치 API 연동
- 요일/공휴일/날씨/행사 데이터 추가
- 정류장 ID 기반 검색 정확도 개선
- 노선 방향성 상행/하행 분리
- 혼잡도 기준을 고정 임계값이 아니라 노선별 분위수 기준으로 개선
- 모델 예측 결과를 실제 API 응답에 직접 반영
- 캐시 파일 크기 최적화
- TypeScript 도입
- API 문서 Swagger화
